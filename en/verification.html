Verification scope

The records below belong to the September 12 source snapshot. The two compilers and KUROSAKI CLI were built from the collected sources. KOKURA and SARAKURA used local executables fingerprinted in the inventory. These checks do not cover all features, peripherals or physical hardware.

Each entry records compilation, a 120-frame emulator run and its screenshot. Pixel comparisons are separate evidence. Exit code zero alone does not prove correct input, sound or game behavior. Build and runtime evidence is documented in publication checks; test inputs and conditions are recorded there.

API examples: expected images and verification

Each tile program was built and run for 90 frames in KOKURA in both DMG and CGB modes. Verification compares the displayed tile pattern and its blank border against the supplied font, checks the expected foreground colors, and reads the on-screen result. The ROM also reads back the target tile and attribute bytes. A zero exit code alone is not the pass criterion. Writes in these examples occur with the LCD off; hardware behavior and LCD-on transfer timing have not been tested here.

__settile

Write one tile-number byte to the tile map; this selects an existing tile image, not new pixel data.

The destination is always 0x9800 + 32*y + x, regardless of which maps LCDC selects for the background and window.

Expected image: the following tile pattern starts at tile coordinates (x=2, y=3), or pixel coordinates (16,24). Each character occupies one 8×8 tile. Read the pattern from top to bottom and left to right; the surrounding tiles remain blank.

Read eight serial bits from expansion input D1 at $4017. Write 1 then 0 to $4016 to latch the controller streams, sample bit 1 eight times, and place successive samples into result bits 0–7. This is one read of the D1 channel for port 2; it does not read the ordinary D0 controller channel or retry for matching samples.

This program contrasts ordinary D0 input with expansion D1 and the microphone's digital level. Hold A on controller 1 and B on controller 2 until the snapshot is captured. NORMAL P1 and NORMAL P2 display 001 and 002. In the supplied KUROSAKI run, D1 PORT 1, D1 PORT 2, EXP ALIAS 1, EXP ALIAS 2, MIC LEVEL and MIC DIRECT all display 000 because those signal lines are not emulated. The displayed values then stay fixed. With suitable peripherals and an implementation of their signal lines, the expansion and microphone values depend on the actual inputs; consult the bit layouts above rather than expecting these zeros.

The published KUROSAKI controller model returns only D0 plus fixed bit 6. D1 and the microphone bit are therefore always 0 in that emulator, even while ordinary controller buttons are held. The supplied run verifies compilation, ordinary-button input and this zero-signal observation. Nonzero peripheral signals, electrical timing and real-device compatibility remain unverified; a zero here is not proof that an attached device works or that these functions cannot read it on hardware.

vram_init

Initialize the deferred VRAM command queue to empty and clear its overflow latch. This does not erase the screen, upload tile graphics or allocate hardware VRAM.

This complete program demonstrates deferred writes, queue accounting and overflow recovery. Seven drawing calls use 7 of 32 command slots on GB, or 52 of 128 command bytes on FC: CAPACITY/USED/FREE reads 032/007/025 or 128/052/076. AFTER FLUSH and FAILED CHECKS must be 000; OVERFLOW SEEN must be 001. An intentional full-queue rejection tests the latch. Reading or flushing does not clear it; clearing the queue does. On FC, an uncommitted direct flush must leave the pending queue intact.

Image coordinates are pixels from the upper-left corner. Expect solid 8 × 8 squares at (16,16) and (32,16), a solid 32 × 24 rectangle at (16,32), and a 40 × 8 horizontal bar at (80,64). The final VBlank write adds an 8 × 8 square at (144,80). The discarded write at (144,24) must leave that cell blank. DMG uses black shapes on white, CGB uses red, blue and green shapes on white, and FC uses white shapes on black. These emulator images do not constitute real-hardware verification.

Three original 8 × 8 patterns distinguish the copy operations: tile 1 is solid; tile 2 fills its left four columns; tile 3 is a left-aligned triangle widening from one pixel at the top to eight at the bottom. At (80,32), the 3 × 2 tile block must read [1,2,3] / [3,0,2], where 0 is blank. Its first source byte changes after queuing, so a solid tile there proves that the source pointer is retained. At (16,64), the copy shows [1,2,3]; at (48,64), the tiles alias shows [2,3]. Their dimensions are 24 × 16, 24 × 8 and 16 × 8 pixels respectively.

In CGB mode, the two upper squares, the three-pattern copy and the final VBlank square are red. The 32 × 24 rectangle and two-pattern copy are blue. The packed 3 × 2 block and 40 × 8 bar are green. Text remains black on white. Color checks cover each drawn pixel as well as geometry.

__cgb_safe_set_svbk

Write the raw WRAM selector SVBK ($FF70) on CGB. Hardware uses bits 0–2; raw values 0 and 1 both map bank 1 at $D000–$DFFF. For example, 8 also maps bank 1. Unlike __svbk_set, this guarded setter permits a dual-mode target and does not return the previous bank.

The complete CGB-only program stores 1 at $D100 in WRAM bank 2 and 2 at the same address in bank 3, then reads both back and restores bank 1. The values choose an 8 × 8 red square at (16,24) and a blue one-pixel 8 × 8 square outline at (16,48). FAILED CHECKS 000 checks raw-selector normalization, bank separation and the previous-bank return for constant, variable, arithmetic and function-result arguments. Six separate invalid-build fixtures verify KQ2103 for DMG/dual targets and KQ2102 for constant banks 0 and 8. Runtime verification uses KOKURA; real hardware and interrupt-driven concurrent bank changes are not tested.
