생성형 AI 게임 개발 프롬프트

요구 사항을 작성한 뒤 프롬프트 전체를 AI에 전달하세요. 구현, 에뮬레이터 테스트, SARAKURA 분석, 수정 후 재검증까지 다룹니다.

KITAQGB · KITAQFC

빌드된 Windows CLI

저장소 루트의 sarakura.exe는 Windows x64용 실행 파일입니다. ZIP을 내려받아 라이선스 문서와 함께 보관하세요. 실행 시 Rust, Python, .NET은 필요하지 않습니다. 아래 빌드 절차는 소스에서 다시 빌드할 때 사용합니다. 독자적으로 작성한 프로젝트 코드는 DAISUKE OBA가 MIT로 제공합니다. 의존 라이브러리의 조건은 BINARY_NOTICES.md와 licenses/에 유지합니다.

1. SARAKURA가 하는 일

SARAKURA는 컴파일러의 빌드 정보와 에뮬레이터의 진단 이벤트를 결합하여, 수정과 재시험에 활용하기 쉬운 형태로 정리합니다. ROM을 실행하는 에뮬레이터는 아니며, C 소스를 알리지 않고 고치는 프로그램도 아닙니다.

2. 도구 빌드

powershell
Push-Location .\sarakura
.\scripts\build.ps1
.\sarakura.exe --help
Pop-Location

짧은 sarakura 명령은 PATH 등록을 전제로 합니다. 등록하지 않았다면 빌드한 실행 파일의 경로를 사용하세요. GB는 gb analyze, FC는 fc analyze를 선택합니다.

3. 첫 분석

입력은 두 가지입니다. --metadata에는 빌드 시 생성된 JSON을, --events에는 실행 중 기록한 진단 JSONL을 전달합니다. JSONL은 한 줄에 JSON 객체 하나씩 저장하는 형식입니다.

powershell
sarakura gb analyze --metadata .\out\build.json --events .\out\gb_events.jsonl --out .\out\report --fail-on error

출력된 report.html을 브라우저로 여세요. 개별 진단을 읽기 전에 대상 기종, 관찰 프레임, 오류 수, 경고 수를 확인합니다. --frames는 분석 조건을 설명하는 값이며, SARAKURA에 그만큼 ROM을 실행하라고 지시하는 옵션이 아닙니다.

4. 입력 자료부터 점검

powershell
sarakura inspect-metadata --metadata .\out\build.json
sarakura inspect-events --events .\out\gb_events.jsonl
sarakura emitter-check gb --metadata .\out\build.json --events .\out\gb_events.jsonl --strict

게임 동작을 조사하기 전에 읽을 수 없는 파일, 서로 다른 대상 기종, 지원되지 않는 이벤트 종류를 먼저 구분하세요. 일반 에뮬레이터 보고서를 events 파일로 넘긴다고 유효한 진단 입력이 되는 것은 아닙니다.

5. 진단 해석

error는 우선 살펴볼 항목, warning은 상황에 따라 문제일 수 있는 항목, info는 판단에 도움이 되는 정보입니다. 심각도는 우선순위를 정하는 도구이며 게임의 의도를 완전히 이해하지는 못합니다. 같은 PC가 반복된다는 관찰만으로 정상적인 타이틀 대기 루프와 멈춤 현상을 구별하기는 어렵습니다.

ROM 해시, 입력 순서, 장면, 화면, 소리, 소스 위치를 대조하세요. 수정 전후 조건이 같아야 합니다. 그렇지 않으면 진단 수가 줄어도 단지 다른 장면을 실행했기 때문일 수 있습니다.

6. 출력 파일

내장 설명, 진단 힌트, 수정 지침은 영어로 출력하며 HTML은 lang="en"을 선언합니다. 사용자가 넣은 문자열과 이벤트 ID는 자동 번역하지 않습니다. 기본 가림 처리는 일부 프로젝트 이름과 경로를 바꾸지만 모든 주소와 관찰 내용을 익명화하지는 않습니다. 비공개 입력의 분석 결과를 공개하기 전에는 보고서 내용을 직접 확인하세요.

파일용도
ai_diagnostics.json자동 처리용으로 정규화한 진단
diagnostic_summary.json개수와 요약
report.html사람이 읽는 보고서
repair_prompt.md수정 조사에 필요한 시작 정보
repair_plan.json / .md수정 순서와 대상
automation_plan.json / .md도구의 기능에 맞춘 작업 계획
retest_plan.json재검사 계획
repro_bundle.zip재현 정보 묶음

계획을 생성하는 것과 실행하는 것은 다릅니다. C 소스나 ROM을 고친 뒤에는 컴파일러, 에뮬레이터, SARAKURA를 다시 실행하세요.

7. 규칙 목록, 필터, 관찰 범위

powershell
sarakura catalog gb --json
sarakura catalog fc --json
sarakura pack-plan gb
sarakura coverage gb --events .\out\gb_events.jsonl --out .\out\coverage.json

catalog는 진단 규칙을 나열하고, pack-plan은 영역별로 묶으며, coverage는 대응하는 이벤트가 관찰되었는지 조사합니다. 규칙 목록에 항목이 있다고 현재 에뮬레이터가 그 이벤트를 반드시 출력하는 것은 아닙니다.

powershell
sarakura gb analyze --metadata .\out\build.json --events .\out\gb_events.jsonl --out .\out\ppu_report --diagnostic-pack ppu --min-severity warn --fail-on error

--diagnostic-rule은 이벤트 이름이나 규칙 ID, --phase는 단계, --diagnostic-pack은 영역을 선택합니다. 필터로 진단을 숨기는 것은 문제 해결이 아닙니다.

8. 수정 전후 비교

powershell
sarakura baseline-delta --baseline .\out\before --current .\out\after --out .\out\delta --markdown .\out\delta --fail-on-new error --fail-on-regression error --enforce

결과는 새로 발생, 해결, 개선, 지속, 악화로 분류됩니다. 남아 있는 문제와 새로 생긴 문제를 구분하세요. 비교할 때 입력, 프레임 수, 진단 필터를 동일하게 유지해야 합니다.

9. 형식 검증과 CI

powershell
sarakura validate .\out\report\ai_diagnostics.json --strict
sarakura ci-summary --diagnostics .\out\report --fail-on error --enforce
sarakura schema export --out .\out\schemas

지속적 통합(CI)은 반복 가능한 검사를 자동화합니다. ci-summary는 --enforce가 있을 때만 프로세스 종료 코드를 바꾸며, 없으면 JSON의 판정을 읽어야 합니다. analyze의 --fail-on error는 오류가 있을 때 0이 아닌 종료 코드를 반환합니다. 기본값 never에서는 진단만으로 프로세스가 실패하지 않으므로 CI에서 정책을 명시하세요. warn을 선택하면 경고도 실패 조건이 됩니다.

powershell
sarakura ci-summary --diagnostics .\out\report --fail-on error --enforce
if ($LASTEXITCODE -ne 0) { throw "The diagnostic failure condition was met" }

스키마 검증 성공은 데이터 형식을 확인했다는 뜻입니다. 게임이 의도대로 작동하는지 알려면 입력, 화면, 소리 시험도 필요합니다.

10. 재현 자료 다루기

normalize-events는 이벤트 기록을 정규화하고 inspect-repro는 재현 묶음을 살펴봅니다. 공유 전에 의도한 ROM의 정보인지, 필요한 입력 절차가 들어 있는지 확인하세요. --allow-project-labels를 지정하면 프로젝트에서 유래한 이름과 식별자를 명시적으로 유지합니다.

11. 작은 연습용 입력

설명서에는 GB·FC용 최소 빌드 메타데이터와 이벤트 예제가 있습니다. GB 합성 보고서와 FC 합성 보고서를 열어 보세요. samples/sarakura_demo.ps1은 이 입력을 분석하는 예입니다. 형식을 배우기 위해 만든 합성 자료이며 실제 ROM에서 수집한 증거가 아닙니다. 실제 ROM 시험에는 KOKURA나 KUROSAKI가 기록한 이벤트를 사용하세요.

12. 한 번의 수정·재시험 주기

  1. 같은 ROM과 입력으로 문제를 재현하고 로그와 화면을 남깁니다.
  2. SARAKURA로 후보를 정리하고 관련 소스를 읽습니다.
  3. 원인에 집중하여 변경합니다.
  4. 다시 빌드하고 같은 조작을 실행합니다.
  5. baseline-delta와 함께 화면, 소리, 게임 동작을 비교합니다.

변경과 결과의 관계를 이해할 수 있도록 이 주기를 작게 유지하세요.
